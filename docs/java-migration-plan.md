# 백엔드 Java 전환 계획

## 목표와 기준

Spring Boot의 기존 API·데이터 계약을 유지하면서 `api`, `application`, `domain`, `batch`의 애플리케이션 소스와 테스트를 Java 21로 옮긴다. 기준은 원본 `main` 커밋 `7c58801a2ae070bdd5733c47b9396a0a3f820986`이다. 가져온 시점에는 Kotlin 파일 575개(주 소스 413개, 테스트 162개)가 있다.

각 전환 작업은 기존 테스트 확인 → 동등한 Java 구현·테스트 → 모듈 테스트 → 전체 테스트 → Kotlin 대응 파일 제거 순서로 진행한다. 외부 API 실호출은 원본 운영 환경을 사용하지 않는다.

## 단계

1. **기준선 고정(완료)**: 가져온 코드의 검증 중복을 해결한 뒤 `./gradlew test`를 통과시켰다. 원본 배포 설정과 프런트엔드가 복사되지 않았음을 확인했다. 이후 작업에서는 API·DB 계약을 기능별로 기록한다.
2. **`batch`(완료)**: 의존 모듈이 Kotlin인 상태에서 Java 혼합 빌드를 먼저 검증했다. 시작점·스케줄러·테스트를 옮겼고 `./gradlew test`와 `./gradlew :batch:bootJar`를 통과시켰다.
3. **`domain`**: 엔티티·enum·저장소·테스트를 기능 묶음별로 옮긴다. JPA 프록시, 생성자, 식별자, 연관관계, 컬럼 이름을 검증한다.
4. **`application`**: 명령·결과, 비즈니스 서비스, 트랜잭션, 보안·외부 연동을 기능 묶음별로 옮긴다. null 처리, 예외·오류 코드, 시간·금액 계산, Redis 동작을 검증한다.
5. **`api`**: DTO·컨트롤러·필터를 옮긴다. `@Valid`, JSON 필드명, 상태 코드, 쿠키·헤더와 API 응답 형식을 검증한다.
6. **빌드 정리**: Kotlin 소스·테스트가 0개이고 전체 테스트가 통과하면 Kotlin 플러그인과 런타임 의존성을 제거한다. Gradle Kotlin DSL 변경 여부는 별도로 결정한다.

## 완료 조건

- 모든 백엔드 애플리케이션 소스와 테스트가 Java다.
- `./gradlew test`와 필요한 API 계약 검사가 통과한다.
- 원본 저장소에 쓰기 가능한 Git 원격, 원본 배포 워크플로, 원본 운영 서비스 호출 설정이 없다.
- 기존 API·데이터 계약과 달라진 부분은 별도 변경으로 명시되어 있다.

전환 중에는 Java와 Kotlin의 혼합 컴파일을 허용한다. 한 번에 전체 파일을 기계적으로 변환하지 않는다.

## 기능 묶음으로 PR 수 줄이기

PR #3 병합 기준(`529dc03`)으로 남은 Kotlin 파일은 566개다. 파일 몇 개마다 PR을 만드는 대신, 모델·저장소·해당 테스트와 필요한 호출부를 기능 단위로 묶는다. 앞으로의 목표는 아래 11개 PR이며, 이번 정책 도메인 시범 작업을 포함한다. 이미 병합한 PR #1~#3은 이 숫자에 포함하지 않는다.

| 영역 | 목표 PR 수 | 범위 |
| --- | ---: | --- |
| `domain` | 3 | 정책 패키지 1개, 나머지 도메인을 의존 관계에 따라 2개로 묶기 |
| `application` | 4 | 인증·회원·공통, 영농·리포트, 정책·검색·외부 정보, 커뮤니티·코칭 등 기능 묶음 |
| `api` | 2 | 인증·공통과 기능별 HTTP 계약을 호출 관계에 따라 묶기 |
| 로컬 통합 검증·빌드 정리 | 2 | 개인 HTTP·DB·Redis 환경 검증, 전환 완료 후 Kotlin 의존성 제거 |

이 숫자는 시범 결과로 조정할 목표다. 후속 PR의 정확한 파일 배정과 실행 범위는 각각 계획을 제시하고 승인받는다. 테스트 실패나 계약 위험 때문에 분리가 필요하면 먼저 수정 계획을 설명한다. Gradle Kotlin DSL 전환과 실제 서버 배포는 포함하지 않는다.

PR을 크게 묶어도 커밋의 역할은 분리한다. 예를 들어 정책 엔티티, 추천 엔티티, 정책 검색, 추천 페이지 조회, 문서 갱신을 서로 다른 커밋으로 기록한다. 제목에는 바뀐 대상과 동작을 명시한다. 해당 전환 때문에 필요한 Kotlin 호출 문법 수정은 같은 커밋에 넣어 각 커밋이 컴파일 가능한 상태를 유지한다. 관계없는 기능·설정·문서를 포괄적인 제목으로 합치지 않는다.

중간에는 영향을 받는 모듈·경계 테스트를 실행하고, 최종 코드에서 `./gradlew clean test :batch:bootJar --no-daemon`을 실행한다. 로컬 커밋을 모아 push하고 Draft PR을 만들어 불필요한 CI 반복을 줄인다. 계획 승인 범위는 Draft PR·CI 확인까지이며 병합은 별도 승인이다.

## 정책 도메인 시범 전환

- 기준: `dev`의 `529dc03`, 작업 브랜치: `refactor/domain-policy-java`.
- `domain.policy`의 남은 Kotlin 주 소스 8개와 테스트 4개를 Java로 전환했다. 기존 Java enum·동기화 작업은 유지한다.
- 주 소스는 `PolicyProgram`, `PolicyRecommendation`, 두 JPA 저장소, 두 조회 인터페이스와 두 조회 구현이다.
- 상위 모듈은 필요한 Kotlin 호출 문법만 바꿨다. 실제 변경은 `application` 7개 파일과 API 검색 통합 테스트 1개 파일이다. 후보였던 `SearchSuggestionService` 주 소스는 수정이 필요하지 않았다.
- 회귀 테스트를 기존 Kotlin 구현에서 먼저 실행했다. 상세 갱신·실패·길이 제한·마감일 경계, 영속성 필드·고유 키·회원/연도 필터·삭제, 검색 공백·대소문자·커서, 추천 정렬·null 날짜·동점·N+1을 검증한다.
- `PolicyProgram` 32개 필드와 `PolicyRecommendation` 5개 필드의 JPA 애너테이션·순서, 두 JPA 저장소의 JPQL 6개를 원본과 대조해 일치를 확인했다. 검색 조건·커서·결과에는 Java `record`를 사용해 값의 동등성을 유지했다.
- 기존 Kotlin `BaseTimeEntity`의 `final` 접근자와 `Member`의 `final` 클래스 때문에 실질적인 JPA 프록시 사용에는 제약이 있다. 이번 작업은 매핑과 기존 동작을 보존하며 공통 기반 클래스·회원 전환은 별도 승인 범위다. 추천 카드 조회의 기존 SQL 수 상한 테스트는 유지한다.
