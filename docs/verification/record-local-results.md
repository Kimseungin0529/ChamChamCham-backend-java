## 거부와 경계에서 확인한 것

1. **부분 저장 방지:** 잘못된 요청의 공통·상세·피드백 행 수가 증가하지 않았다. 형식검증 실패와 저장 도중 실패를 분리했다.
2. **실제 수정 rollback:** 관수 기록을 병해충 기록으로 수정하면서 존재하지 않는 농약을 지정했다. 서비스가 기존 상세 삭제/flush 이후404로 실패해도 이전 공통행·관수상세·피드백이 모두 복원됐다.
3. **수량 반올림:** `1.23456`은 DB의 scale4로 `1.2346`이 됐다. 조회와 AI 입력도 이 저장값을 사용했다. 원문과 숫자가 완전히 동일하다고 주장하면 안 된다.
4. **API와 DB 한도 차이:** 가상 자재명256자와 정밀도 초과 수량은 API형식 검사를 지나 DB에서 실패해500으로 처리됐다. 응답은 일반 오류코드 `COMMON_999`이고 부분 저장은 없었다. 이 동작을 바람직한 정책으로 승인한 것은 아니다.
5. **등록관계 미검사:** 가상 농약·병해충 ID가 존재하면 적용관계가 없어도 저장됐다. 등록 적합성 검증과 기록 저장은 구분해야 한다.
6. **선택하지 않은 상세:** 유효한 무관 상세는 저장되지 않지만, 무관 상세가 형식검증을 위반하면 전체 요청이 거부됐다.
7. **소유권:** 다른 회원의 기록 조회·수정은403, 다른 회원 농지로 생성은404였다.
8. **기본값·명칭:** 수확 출처 생략은CULTIVATED, 명시null은거부였다. 수확량모름은 요청/응답의 필드명이 달랐다.

## 검토에서 보완한 검증 도구

- 비교 기록이 mutable 입력 객체를 참조해 나중 수정에 영향을 받던 문제를 재현했다(90개 중1개 실패). `deepCopy()`로 입력을 보관한 뒤 같은 검증이 통과했다.
- API형식 검사에서 거부되는 수정과 서비스 내부에서 실패하는 수정 rollback을 별도로 검증했다.
- 농지·작물·작업시각·기록날씨·기온의 공통값 대조와 enum별 프롬프트의 독립된 기대 문구도 추가했다.
- 검토에서 critical은 없었으며 important2건은 위와 같이 반영했다. 두 참고 검증 한계도 보완했다.

## 이해해야 할 의미와 남은 검증

이번 결과는 **입력한 데이터가 어떤 형태로 저장되고 모델에게 전달될 준비가 되는지**에 대한 증거다. 농업 지식의 정확성, 검색 품질, 실제 모델의 표현 준수, 실제 농약 사용 적합성의 증거가 아니다.

농약 명칭과 프롬프트 표현은 수정하지 않았다. “총살포량=최종혼합살포액”이라는 사용자 확인과 “약을 섞은 물의 양”이라는 실제 프롬프트 표현의 차이가 남아 있다.

HTTP 처리는 MockMvc의 실제 컨트롤러·서비스와 PostgreSQL을 사용했다. 별도TCP서버·JWT로그인·외부날씨·실제AI·실벡터검색·비동기보고서생성은 실행하지 않았다. 시각과 날씨는 합성 고정값이다. 534개 작물 각각의 DB·코칭 품질을 검증한 것은 아니다.

후속 큰 작업에서는 공식 문서별 지원 작물·작업·상황을 정하고 적재·실검색을 검증한다. 그다음 실제 모델을 연결한 기록·코칭API 검증을 별도 플랜으로 제안한다.
