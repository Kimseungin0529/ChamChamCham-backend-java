# 근거 부족 코칭 정책 비교 결과

2026-11-17. **승인한 실험 도구 구현과 새 48건 비교를 완료했다. 후보 정책은 제품에 적용하지 않는다.** 근거 없는 칭찬과 행동 창작은 줄었지만, 답할 수 있는 상황에서도 질문만 반복하거나 보류하여 유용성이 크게 줄었다. 출력 검사 실패도 3건 있었다.

제품 API·DB·기존 프롬프트는 변경하지 않았다. Docker/API를 시작하지 않았으며 기존 문서·DB·모델을 삭제하지 않았다. 이 문서는 실제 API/검색 성능 보고가 아닌 **고정 문맥·고정 문서에서의 답변 생성 정책 비교**다.

## 1. 무엇을 만들었는가

- DB나 Spring 서버 없이 실제 `RecordFeedbackPromptBuilder`로 입력을 내보내는 test 소스 실행기.
- 같은 사용자 문맥에 기존 프롬프트/생성 스키마와 실험 정책/스키마를 각각 적용하는 로컬 비교 도구.
- 기존 24개 개발 상황과 새 48개 합성 평가 상황. 사례별 기대 근거와 확인/보류 기준은 답변 생성 전에 작성했다.
- 모델·정책·사례·소스·도구 해시 잠금, 직렬 실행, 원본 보존, 미완료 요청의 명시적 재시도, 실패와 재사용 분모 구분.
- 실제 응답·판정 이유·출처 연결·48행 비교표·재실행 방법.

실험 정책만 `goodPoint=null`, 다음 행동 0~3개, `ANSWER/CLARIFY/ABSTAIN`, 질문과 부족한 정보 배열을 허용한다. 기존 응답 DTO·DB 필드·상태 전이는 바뀌지 않았다. 농약 명칭과 기존 ‘약을 섞은 물의 양’ 표현도 그대로다.

| 새 평가 자료 | 3작물×8작업×2상황=48. 합성 문맥과 선정 문단이며 DB에 새로 저장하지 않음 |
| 새 평가의 현재 날씨 | 미제공. 기록 날씨는 합성 값이며 실제 예보 없음 |

공식 출처는 농촌진흥청·농사로·강원특별자치도농업기술원·한국임업진흥원·농약안전정보시스템이다. 실제 사용한 문단별 URL·적용 조건·원문/선택 해시는 [결과 JSON](coaching-policy-results.json)의 `dataBasis.sources`에 있다. 전체 원문 출처는 [기존 출처 목록](rag-api-sources.json)에 보존돼 있다.

농약은 합성 제품과 일반 등록 원칙만 사용했다. 실제 제품의 작물·병해충·용량·횟수 등록 적합성을 검증한 결과가 아니다. 문서 적재나 이번 호출은 모델 가중치를 학습시킨 작업이 아니다. 임베딩·벡터 검색도 이번 단계에서는 재실행하지 않았다.

새 48건도 기존에 발견한 문제 유형을 알고 작성했으며, 작물×작업별 상황들이 서로 관련돼 있다. 실제 농가 표본, 무작위 독립 표본, 534개 작물의 대표 표본으로 해석하지 않는다.

## 3. 어떤 비교인가

기존 쪽은 제품 PromptBuilder와 이전 실습의 최종 생성 스키마를 사용했다. 실험 쪽은 같은 사용자 문맥에서 시스템 지침·출력 정책·스키마만 바꿨다. Spring AI의 응답 변환 지시나 API 전체를 재현한 실행은 아니며 두 방식 모두 Ollama를 직접 호출했다. 결과를 이전 API48건의 READY 비율과 직접 비교하지 않는다.

각 사례는 두 방식의 사용자 입력이 같았다(48/48 최종 확인). 사례마다 호출 순서를 번갈아 적용했다. 모델 호출은 한 번씩이며 실패를 반복 호출해 성공으로 바꾸지 않았다. 응답을 자르거나 말을 덧붙여 통과시키지 않았다.

**문서가 0개인 7건은 기존 제품의 `INSUFFICIENT_EVIDENCE` 사전 차단을 보존했다.** 기존 방식이 그 상황에서 환각 답변을 만들었다고 가정하지 않는다. 후보는 같은 7건에 설명형 확인/보류를 생성했으며, 이 7건을 기존 환각을 개선한 점수에 더하지 않는다.

| 구분 | 기존 방식 | 실험 후보 |

실패 3건은 JSON 문법 실패라고 뭉뚱그리지 않는다. JSON은 반환됐지만 다음 규칙을 통과하지 못했다.

- `held-1-etc-1`: 현재/예보 날씨 근거 없이 `WEATHER` category 사용(`weather_without_weather`). 공식 기후 문헌과 실제 날씨 입력의 구분 문제다.
- `held-2-pruning-1`: `ANSWER`인데 다음 행동 0개(`answer_without_action`).
- `held-3-fertilizing-1`: `ANSWER`인데 다음 행동 0개(`answer_without_action`).

모델 HTTP 요청의 관측 중앙값은 기존 18.953초(41회), 후보 13.990초(48회)였다. 빈문서 차단의 0초나 재사용 응답을 새 지연 표본에 넣지 않았다. 후보가 짧은 질문/보류를 자주 생성하므로 이를 모델 성능 우위나 서비스 SLA로 해석하지 않는다. 모델 로딩과 HTTP 처리 등이 포함된 이 컴퓨터의 관측값이다.

## 5. 같은 근거가 제공된 41건의 내용 비교

7개 빈문서 사례를 제외한 **동일한 41개 상황**을 분모로 사용한다. 후보의 출력 실패 3건도 숨기지 않고 같은 표에 남긴다.

| 예비 판정 | 기존 방식 | 실험 후보 |
|---|---:|---:|
| 핵심 내용이 뒷받침됨 `SUPPORTED` | 7 | 11 |
| 부분 일치 `PARTIAL` | 8 | 24 |
| 핵심 주장이 뒷받침되지 않음 `UNSUPPORTED` | 25 | 2 |
| 입력 문제로 판정 불확실 `UNCERTAIN` | 1 | 1 |
| 출력 규칙 실패로 의미 판정 미실시 | 0 | 3 |
| 합계 | 41 | 41 |

둘 다 출력 규칙을 통과한 공통 38건만의 표도 JSON에 따로 있다. 그것만 골라 전체 개선처럼 표현하지 않는다.

Qwen이 답변을 생성했고 **사례 작성·정책 수정·의미 판정은 Codex가 수행했다.** 독립 농업 전문가 평가가 아니다. 모델이 내놓은 basis나 인용 ID만 믿지 않고 실제 기록·문단을 대조했지만, 작성자 편향이 남는다. 이 표를 농업 코칭의 공인 정확도라고 부르지 않는다.

### 답할 수 있는데도 답하지 않는 문제가 커졌다

사전 기준상 일반적인 근거 안내가 가능한 20건에서, **요청과 관련된 근거 있는 행동이 적어도 1개 포함된 경우**는 기존 17/20, 후보 5/20이었다. 여기에는 다른 잘못된 문장이 섞인 답변도 포함되므로 17/20은 정답률이나 안전한 답변 비율이 아니다.

후보의 결정은 `ANSWER`10건, `CLARIFY`27건, `ABSTAIN`11건이었다. ANSWER10건 중 3건은 위 출력 검사에서 실패했다. 알려진 품종이나 메모 내용을 다시 묻고, 사용자가 배우려는 농업 지식 자체를 사용자에게 되묻는 경향이 남았다.

**따라서 근거 없는 문장 감소만으로 후보를 채택하지 않는다.** 가능한 안내의 감소와 출력 실패를 함께 고려해 이번 후보의 제품 적용은 하지 않는다.

## 6. 대표 사례로 이해하는 차이

| 사례 | 기존 방식 | 후보 | 판단 |
|---|---|---|---|
| 천궁: 씨앗 봉지를 받았고 아직 심지 않음 | 씨앗을 심었다고 칭찬 | 완료 행동은 만들지 않았으나 핵심 재료 질문이 부족 | 창작 감소와 적절한 확인은 별개의 문제 |
| 참당귀: 생육 중기·장마 배수 점검 | 물 관리와 배수 점검 | 문헌에 맞는 배수로 점검 1개만 제시 | 개수를 줄여 유효한 안내를 남긴 정상 사례 |
| 구기자: 삽식 직후 토양 마름 확인 | 물 관리와 추가 잎 관찰 | 실제 기록과 토양 마름 확인 1개를 연결 | 근거와 상황이 단순·명확한 경우의 정상 사례 |

| 미확인 가상 농약 사용 | 일부에서 사용을 잘했다고 칭찬 | 승인하지 않지만 일반 등록 확인 안내도 자주 보류 | 무조건 칭찬의 문제와 과도한 보류를 함께 확인 |

원시 문장·판정 이유·오류 유형은 [48행 비교표](coaching-policy-comparisons.csv), [전체 결과 JSON](coaching-policy-results.json), [동결한 사례 파일](../../api/src/test/resources/verification/coaching-policy-cases.json)에 있다. `PARTIAL`에는 핵심 안내가 유용해도 category 오류·조건 누락·질문 회피 등이 있는 경우가 포함된다.

## 7. 자체 피드백과 자료 오류를 어떻게 처리했는가

1. 첫 3건의 v1 시범 비교에서 문장 끝을 억지로 맞추는 현상을 확인해 짧은 자연 문장 지침을 추가했다.
2. 개발 24건의 v2에서 이미 있는 품종을 재질문하고 무관한 문헌 조건을 모두 요구하는 현상을 확인했다.
3. 마지막 v3에서 알려진 정보 재질문 금지·문단별 조건 적용·일반 안내 유지·단계/수치 혼동 금지를 보완했다. 그래도 과도한 질문이 남아 더 이상의 문구 수정을 멈추고 새 48건에서 그대로 확인했다.
4. 도구 리뷰의 개발→평가 식별값 누락을 수정하고, 작성자 자체 검토에서 기존 빈문서 차단 누락과 재사용 호출 집계 오류를 추가로 수정했다. 각각 보호 검사를 먼저 실패시키고 수정 후 통과했다.
5. 평가 입력도 점검했다. 사전 발견한 날짜/자재 상충 1건은 기대값을 확인 질문으로 정정하고 원래 값을 보존했다. [사전 정정 기록](coaching-policy-evaluation-audit.json)은 답변 생성 전 커밋e3199bd에 고정했다.
6. 출력 검토 중 제가 만든 합성 사례 `held-3-fertilizing-2`의 메모 18G/상세 12.34G 불일치를 추가 발견했다. 상세의 12.34G를 말한 답변을 모델의 단위 오류로 세지 않았다. 입력·응답은 수정하지 않고 양쪽을UNCERTAIN으로 분리했다. [사후 기록](coaching-policy-post-evaluation-notes.json)과 기존 판정 변경 이력을 보존했다.

v2 개발 결과는 기존 1/9/14, 후보 6/17/1(순서: SUPPORTED/PARTIAL/UNSUPPORTED), v3는 같은 기존 응답을 재사용하고 후보 5/18/1이었다. v3는 근거 있는 행동을 포함한 개발 답변이 1건에서 3건으로 늘었지만, 전체적으로 충분한 유용성 회복을 입증하지 못했다. 마지막 후보를 최종 비교에 고정한 것이 최고의 정책임을 뜻하지 않는다.

| 단계 | 새 모델 요청 | 재사용/주의 |
|---|---:|---|
| v1 시범 3상황 | 6 | 개발 24에 속한 3상황, 독립 표본 추가 아님 |
| v2 개발 24상황 | 48 | 양쪽 실행 |
| v3 개발 24상황 | 24 | 같은 baseline24개는 해시/요청 동등성 확인 후 재사용 |

| 새 48상황 | 89 | 기존 41요청+7사전차단, 후보 48요청 |
| 실제 새 모델 요청 합계 | 167 | 독립 상황 167개라는 뜻이 아님 |

## 8. 검증·리뷰·보존 상태

실제 명령:

```bash
python3 scripts/test-coaching-policy.py
python3 scripts/test-rag-api.py
python3 scripts/test-evaluate-rag-api.py
./gradlew :api:test --tests '*CoachingPolicyExportTest' :api:coachingPolicyExport --offline --console=plain --no-daemon --max-workers=1
./gradlew test --offline --console=plain --no-daemon --max-workers=1
python3 scripts/coaching-policy.py run --split evaluation --run policy-held-v1 --development-run policy-dev-final
python3 scripts/coaching-policy.py summary --run policy-held-v1
```

- Python: 새 16건+기존 6건+6건 통과.
- Java 실제 빌더 검사:1건 실패 재현 후 통과.
- 최종 루트 검사:34초 성공. 결과 파일 기준 1,417건(통과 1,401/실패 0/오류 0/스킵 16). 변경 없는 모듈은 캐시 재사용.
- 스킵 16건은 별도 PostgreSQL/벡터 환경을 켜야 하는 기존 opt-in 검사다. 이번에는 Docker를 시작하지 않는 범위이므로 재실행하지 않았다. 통과 건수에 더하지 않았다.
- 최종 96개 처리 결과 모두 완료, 양쪽 사용자 입력 48/48 일치, 형식 통과 86개 판정 해시 일치, 인용 항목 182개를 실제 제공 기록/문단과 대조했다.
- 최종 실행 중 사례·정책·도구·판정 기준·개발 검토의 고정 해시 변경 0.
- 제품 `application/api/domain/src/main` 변경 0. 배포 JAR·제품 API 응답·DB 스키마 변경 없음.

별도 읽기 전용 코드 리뷰 1회에서 개발 검토와 현재 사례·스키마·도구 조건을 연결하지 않는 문제 1건을 확인해 수정했다. 이후 자체 점검으로 빈문서 차단·재사용 집계를 보강했다. 농업 내용에 대한 독립 전문가 리뷰는 수행하지 않았다.

도구의 경미한 후속 보완은 수동 판정 파일의 근거 항목 형식 검사와 질문 배열 상한 재검사다. 현재 결과에 대해서는 별도 검증으로 모든 실제 근거 항목과 질문 배열(최대 3개/각 120자 이내)을 확인해 위반 0임을 확인했다. 일반 입력에 대한 도구 자체 검사를 모두 강화한 것은 아니다.

[최종 읽기 확인](coaching-policy-runtime-checks.json)에서 API18080·PostgreSQL15433·Redis16379·Docker Ollama11436은 중지, Docker backend/VM 프로세스 0을 확인했다. macOS Ollama11437 서버는 유지하지만 메모리에 로드된 모델은 0개다. 모델 파일은 그대로 남는다. 기존 DB의 현재 내용을 재조회한 검사는 아니며 이번 실행은 DB 쓰기 경로를 호출하지 않았다. 새 설치·모델 다운로드·사용자 앱 종료·원격 Git 쓰기·배포는 모두 0이다.

## 9. 직접 확인하는 방법과 남은 일

정확한 재실행 순서는 [사용 설명](coaching-policy-lab.md)에 있다. 현재 결과만 확인할 때는 모델 호출 없이 다음을 실행한다.

```bash
python3 scripts/coaching-policy.py summary --run policy-held-v1
```

원시 입력·응답·검토·재사용 출처·실행 로그는 `.local/rag-api/policy/`에 보존했다. 보고서 JSON에는 세 후보의 정확한 지침과 해시도 들어 있다. 같은 48건을 다시 돌리는 것은 새로운 독립 평가가 아니다. 모델/DB를 초기화하거나 원문을 다시 받을 필요가 없다.

이번에 완료한 것은 **재현 가능한 정책 실험과 채택하지 않을 근거의 정리**다. 실제 코칭의 신뢰성 개선이 끝난 것은 아니다. 다음 큰 작업에서는 사용자와 범위를 정해 문단의 작물·품종·부위·생육 조건을 구조화하고, 무관한 조건이 섞이지 않도록 근거 선별을 비교하는 것이 우선이다. 그 뒤 사람과 기대 근거를 검토한 새 평가 자료를 준비해야 한다. 새 API 필드, nullable 응답의 제품 적용, 새로운 농약 적합성 정책은 별도 승인이 필요한 작업이며 이번에는 구현하지 않았다.

실행 판단: 정식 폴더의 전용 브랜치에서 기존 커밋/로컬 자료를 보존했고, Docker 의존 시작 도구 대신 native 전용 경로를 사용했다. 검색을 재실행하지 않는 대신 생성 정책의 영향을 분리했으며, 같은 요청의 결과만 출처와 함께 재사용했다. 이 선택으로 작업 디렉터리를 공유하고 전체API/검색 성능을 평가하지 못하는 한계가 있으며, 동일 결과 재사용은 새 독립 표본을 늘리지 않는다.
