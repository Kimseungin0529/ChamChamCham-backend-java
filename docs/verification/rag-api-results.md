# 로컬 영농 기록 코칭 API 실측 결과

2026-11-15. 승인된 야간 실행 계획의 결과다. **이 컴퓨터에서 실제 API를 직접 실행할 수 있는 환경을 구축했다. 답변을 농업적으로 신뢰할 수 있다는 결론은 나오지 않았다.** 프로그램 동작, 데이터 보존, 근거 검색, 답변 형식, 답변 내용의 근거 일치를 구분한다.

## 1. 지금 직접 해볼 수 있는 것

정확한 전체 사용법은 [rag-api-lab.md](rag-api-lab.md)에 있다. 저장소 루트에서 다음 순서로 실행한다.

```bash
cd /Users/kimseungjin/develop/ChamChamCham-backend-java
python3 scripts/rag-api.py up
python3 scripts/rag-api.py native-up
python3 scripts/rag-api.py start
python3 scripts/evaluate-rag-api.py --export
python3 scripts/rag-api.py submit --file .local/rag-api/requests/dev-1-watering-0.json
```

이미 실행 중이면 `start`가 중복 실행을 거부하므로 기존 서버를 사용한다. 요청 JSON의 `workedAt`, 메모, 상세를 직접 수정할 수 있다. 응답 `data.id`를 아래 UUID 자리에 넣는다.

```bash
python3 scripts/rag-api.py get --record 기록UUID
python3 scripts/rag-api.py feedback --record 기록UUID
python3 scripts/rag-api.py update --record 기록UUID --file .local/rag-api/requests/dev-1-watering-0.json
python3 scripts/rag-api.py regenerate --record 기록UUID
```

재생성은 현재 계약에서 `FAILED`만 허용한다. `READY` 재생성은 409다. 기록 수정은 새 revision의 코칭을 생성한다. 초기 조회는 `PENDING`, 성공은 `READY`, 실패는 `FAILED`와 오류 코드다. 실제 로그인·JWT 인증을 사용하며, 도구가 비밀번호와 JWT를 출력하지 않는다.

중지·재시작·백업 명령은 다음과 같다. 중지는 DB·문서·모델을 삭제하지 않는다. 백업 복구 비교는 API를 멈추고 PENDING이 없는 상태에서 한다.

```bash
python3 scripts/rag-api.py stop-api
python3 scripts/rag-api.py backup
python3 scripts/rag-api.py verify-restore
python3 scripts/rag-api.py stop
# 다음 사용: up → native-up → start
```

## 2. 무엇을 실제로 연결했는가

합성 회원의 실제 비밀번호 로그인 → JWT 보안 필터 → 기록 HTTP API → PostgreSQL 실제 서비스·저장소·트랜잭션 → 비동기 문맥 조립 → 실제 bge-m3 임베딩·pgvector 검색 → 로컬 Qwen 답변 → 기존 출력 검증기 → 상태·답변 조회를 연결했다. 인증을 통째로 끄거나 답변을 수동으로 고쳐 성공시키지 않았다.

날씨는 고정 32℃/맑음, 출처 `SYNTHETIC_LAB`이며 예보는 없다. 보고서 재계산은 테스트 대역이다. 소셜 로그인·메일·음성·사진·실제 날씨 제공자·보고서 AI는 호출하지 않았다. 앱의 모든 외부 통신 기능을 네트워크 차원에서 차단했다고 주장하지 않는다. 이번에 실행한 경로가 이들을 사용하지 않는다.

전용 API는 `127.0.0.1:18080`, PostgreSQL은 `15433`, Redis는 `16379`, macOS Ollama는 `11437`이다. Docker CPU 대조 서버 `11436`은 기본 중지한다. API는 배포 JAR에 들어가지 않는 명시적 test 소스 실행기다. 일반 프로필의 OpenClaw 경로는 유지했다.

## 3. 자료와 모델: 복원·학습과 구분

공식 원문 **9개에서 선택한 26개 문단**을 적재했다. 기관·날짜·적용 조건·선택/제외 범위·해시는 [출처 목록](rag-api-sources.json), [제외 목록](rag-api-source-exclusions.json)에 있다. 농촌진흥청·농사로·강원특별자치도농업기술원·한국임업진흥원·농약안전정보시스템 자료를 사용했다.

- 천궁: 일천궁/토천궁 번식, 일천궁 간격 실험, 고온·수분 관리, 뿌리줄기 수확.
- 참당귀: 일당귀와 종 구분, 종자/육묘/이식, 배수·피복, 뿌리용/직파 관리, 잎/뿌리 수확. 2024년 12월 매뉴얼의 이미지 PDF는 로컬 OCR 뒤 실제 페이지를 대조해 필요한 5문단만 전사했다.
- 구기자나무: 2024년 청감 품종 자료와 2013년 일반 매뉴얼을 구분했다. 비료 표·본문의 정량 상충 부분, 과거 농약 용량, 의약 효능·조리법·가격은 제외했다.
- 농약: 일반 등록 원칙만 있다. 합성 제품의 실제 등록 작물·병해충·용량·횟수 자료나 적합성 판정 기능은 없다.

`bge-m3`는 기존 가중치를 보존·복사해 사용했다. 문서 벡터는 **1,024차원, 코사인 거리, HNSW**, 검색 임계값은 기존 `0.5`다. 임베딩은 검색을 위한 수치 표현이며 농업 답변 모델을 새로 학습시킨 것이 아니다. 원래 팀원의 OpenClaw 설정이나 원본 문서 DB를 복원한 것도 아니다.

기본 답변 모델은 `qwen3:4b-instruct` Q4_K_M, 대조 모델은 `qwen2.5:7b-instruct-q4_K_M`이다. 신규 다운로드 layer 합계 **7,180,380,161바이트**로 승인한 10GB 이내다. 두 모델 모두 보존했다. `temperature=0`, `seed=42`, 문맥 8,192, 생성 상한 1,024, 동시 실행 1, 모델/임베딩 요청 240초다.

Docker CPU에서는 한 개발 기록이 두 번의 요청 제한을 넘겨 약 512초 뒤 실패했다. 공증된 macOS Ollama 0.40.16을 별도 로컬 경로에 설치해 Apple M1 Pro GPU를 사용했다. 같은 개발 상황은 약 35.6초에 성공했다. 기록 시각과 실제 프롬프트가 완전히 동일한 대조 실험이 아니므로 정확한 배속 개선으로 환산하지 않는다. 7B도 한 개발 사례에서 약 95.2초 뒤 형식 실패해 기본 4B를 유지했다. 한 사례로 모델 전체의 우열을 결론내리지 않는다.

## 4. 48건 baseline: 무엇을 의미하는 수치인가

개발용 24건과 평가용 48건은 **3작물 × 8작업**을 바탕으로 만든 합성 상황이다. 평가용은 각 조합 2건이다. 답변을 보기 전에 상황·최소 기대 근거·판정 기준을 고정했다. 실제 농가 표본, 무작위 분포, 534개 작물 전체에 대한 독립 표본이 아니다. 기록 시각은 실행 당시 11월이고 날씨는 합성 32℃로 고정했으므로 실제 계절·기상 조합을 대표하지도 않는다. 이 수치로 원래 팀 서비스의 성능을 재현했다고 표현할 수 없다. 메모에 혼동 방지 문구를 넣은 인위적 스트레스 사례도 포함된다.

다음은 **사실성 지침을 보완하기 전**, 설정을 고정해 한 번 실행한 `independent-v1` 결과다. 이후 이 결과를 보고 고른 8건은 조정용으로 전환했으며 새 독립 점수에 더하지 않는다.

| 항목 | 실측 | 의미 |
|---|---:|---|
| 실행 완료 | 48/48 | 미실행·중단 0 |
| 예상 HTTP 결과 | 48/48 | 정상 접수 45, 예상 거부 3 |
| 거부 요청의 부분 저장 방지 | 3/3 | 필수 `growthPeriod` 누락; 수량 모름 자체가 거부 이유는 아님 |
| 검사 대상 입력→조회→DB AI 문맥 값 보존 | 45/45 | 정상 접수 건. 수량·단위·선택값과 실제 제품 속성을 대조 |
| 최소 기대 문단 회수 | 30/30 | 기대 문단을 지정한 정상 접수 상황만 분모. 전체 검색 정확도 아님 |
| 다른 작물 메타데이터 문서 | 0 | 같은 작물 내 품종·부위·조건까지 적절하다는 뜻은 아님 |
| 형식 검증 후 답변 생성 | 38/45 (84.4%) | `READY` 38, `STRUCTURED_OUTPUT_INVALID` 7 |
| 검증 도구의 전체 관측 시간 | 중앙값 33.870초 | 접수 45건, 최소 27.623 / 최대 68.395초. 실패 재시도 포함 |

미생성 7건은 당시 `STRUCTURED_OUTPUT_INVALID`로 기록됐으나, 원시 trace를 대조하니 모두 모델의 HTTP 오류(`TransientAiException`)가 두 번 발생했다. 제품 검증기가 정상 JSON을 거부한 것만으로 해석하지 않는다. 뒤에서 HTTP 오류 분류와 로컬 생성 문법을 수정했다. 원래 결과 파일의 상태·오류 코드는 소급 변경하지 않았다. `READY`도 기존 검증기의 JSON·길이·말투 조건 통과이며, 모든 문장이 자연스럽거나 프롬프트의 모든 지시를 따른다는 뜻은 아니다.

관측 시간에는 DB 사전 수량 조회, 2초 간격 상태 조회와 최종 DB/응답 수집이 포함된다. 순수 HTTP 응답 시간은 아니다. 모델 호출 자체는 성공 38회(중앙 30.292초, 24.134~36.190초)와 실패 14회(중앙 30.641초, 7상황의 각 2회)를 별도로 기록했다.

시간은 이 컴퓨터에서 관측한 값이며 전용 부하 실험이나 서비스 SLA가 아니다. 간헐적인 개발 검사와 시스템 부하의 영향이 있을 수 있다. 최초 CPU 자료는 중단 후 조회한 시간과 전체 생성 시간을 구분해 별도 한계 파일을 남겼고 위 45건 통계에 섞지 않았다.

### 답변 내용은 별도로 대조했다

Codex가 실제 기록과 인용 문헌을 대조한 **예비 검토**다. 농업 전문가·사용자·농장 효과 검증을 받지 않았다. 형식 통과한 38건의 분류는 다음과 같다.

| 분류 | 건수 | 판정 의미 |
|---|---:|---|
| 충분히 뒷받침됨 `SUPPORTED` | 4/38 | 핵심 행동·근거가 기록/문헌과 일치 |
| 부분 일치 `PARTIAL` | 8/38 | 조건 확인·인과 설명·질문 대응 등의 한계 |
| 뒷받침되지 않음 `UNSUPPORTED` | 26/38 | 행동 창작, 미확인 적합성 판단, 품종/부위 혼동 등 |

생성 실패 7건과 API 거부 3건은 답변 내용 평가에 포함하지 않았다. **4/38을 농업 코칭의 공인 정확도로 부르지 않는다.** 개별 판정 이유를 [결과 JSON](rag-api-independent-results.json), [48행 비교표](rag-api-independent-results.csv)에 공개해 재검토할 수 있게 했다.

특히 품종이 확인되지 않은 구기자 정상 접수 13건 모두에서 청감 재배 문단이 검색됐다(사례별 중복을 허용한 문단 수 46). 이는 조건 확인이 필요한 근거의 혼입 관찰이며 모두 무관한 문서라는 판정은 아니다. 실제 답변에서는 9개 사례에 품종 적용 범위 문제가 표시됐다. [조건부 근거 분석](rag-api-conditional-evidence.json)에 정의와 사례를 남겼다. 전체 문서별 관련성 정답셋과 검색 precision은 이번에 만들지 않았다.

## 5. 대표 사례와 ‘왜’

[입력→DB→조회→실제 프롬프트 예시](rag-api-flow-examples.json)에 원시 비교값과 답변을 함께 남겼다.

- **정상 연결:** 일천궁의 마른 흙을 확인하고 물을 준 기록에서, 문헌의 고온·수분 관리와 잎 관찰을 안내했다. 단순 HTTP 성공이 아니라 실제 저장값과 인용 내용까지 대조했다.
- **단위 보존:** 참당귀 합성 방제에서 농약 `3.5 G`와 총살포량 `1600 ML`이 구별됐다. 실제 프롬프트도 각각 그램/밀리리터였다. 이는 농도·등록 적합성 검증을 뜻하지 않는다.
- **제품명 차이:** API `pesticideName`은 DB `itemName`, AI 문맥의 동일 이름 필드는 `brandName`이었다. 비교 도구가 처음 같은 문자열을 기대한 가정을 고쳐 실제 DB 속성과 각각 대조했다. 제품 명칭이나 계약은 바꾸지 않았다.
- **수확 부위:** 참당귀는 카탈로그 기본 부위가 뿌리/껍질이어도 실제 잎 수확이 AI 입력에 전달됐다. 반면 구기자 뿌리껍질 수확에서는 입력은 맞는데 답변이 열매 색으로 수확을 안내했다. 저장 정합성과 답변 해석의 문제를 분리해야 하는 이유다.
- **행동 창작:** 토양 검사 결과가 없다고 썼는데 검사를 확인했다고 칭찬하거나, 방제를 관수로 바꿔 칭찬했다. 문서 회수 성공만으로 사실성을 보장할 수 없다.
- **조건 일반화:** 청감 품종용 혼식/수형 수치를 품종 미상 기록에 적용했다. 작물명만 맞춰 검색하는 구조의 한계다.
- **API 거부:** `growthPeriod: null`인 수확은 400이며 DB 부분 저장이 없었다. 모델이 대답하지 않은 것을 품질 실패나 올바른 농업 판단으로 세지 않았다.

총살포량은 사용자 확인대로 **농약과 물을 합친 최종 희석액 전체량**으로 해석했다. 기존 프롬프트의 ‘약을 섞은 물의 양’은 지시대로 유지했다. 둘의 표현 차이를 관찰 사항으로 남겼으며 물만의 양이나 희석 배수를 새로 계산하지 않았다.

코드·필드·자료 관계 전체는 [관계 설명](rag-api-data-relations.md), [25필드 표](rag-api-fields.csv), [24개 작물×작업 범위표](rag-api-support-matrix.csv)에 있다. 기존 51사례군/90개 PostgreSQL 검사의 구조 검증은 재사용했다. 이번 48건으로 모든 enum·모든 자유 메모·534작물의 모든 조합을 전수 검사했다고 주장하지 않는다.

## 6. 무엇을 바꾸고 무엇을 채택하지 않았는가

1. 실습 프로필에서만 Spring AI가 Ollama를 직접 호출하도록 구성했다. 일반 OpenClaw 경로와 기존 API/DB 계약은 유지했다.
2. CPU 지연을 실측한 뒤 공식 서명·공증을 확인한 macOS Ollama로 전환했다. 원본 Docker 모델 캐시는 보존했다. 더 큰 7B가 낫다고 가정하지 않고 한 실패 사례를 비교한 뒤 4B를 유지했다.
3. 제품 출력 검증의 길이·개수 조건을 Ollama JSON Schema에도 전달했다. 제품 검증기를 느슨하게 하거나 답변을 자르거나 덧붙이지 않았다. 개발 24건의 21건 통과 후 실패 3건+대조 1건의 선택 회귀는 4/4 통과했다. 이를 24건 전체를 최종 설정으로 다시 실행한 것으로 표현하지 않는다.
4. 지연 실행되는 `ChatClient.entity()`의 네트워크/제공자 HTTP 오류를 JSON 파싱 오류로 잘못 분류하던 구현을 수정했다. 기존 파싱 오류의 재시도는 유지하고 실제 호출 실패는 `CHAT_UNAVAILABLE`로 분리했다. 회귀는 초기 19건, 제공자 오류 추가 후 20건으로 검증했다.
5. 행동 창작·품종 일반화를 막는 사실성 문구를 추가해 선택 8건을 실제 재검사했다. 8/8이 생성됐지만 핵심 근거 문제는 8/8에 남았다. 일부 문장은 달라졌지만 개선을 입증하지 못해 **이 프롬프트 변경은 미채택**하고 원본 해시와 같은 코드로 복귀했다. [정확한 추가 지침·판정](rag-api-grounding-experiment.json)을 보존했다.
6. 수정 경합 검사에서 모델 HTTP500이 추가로 발생했다. 원시 서버 로그에서 생성 문자열의 따옴표가 JSON을 깨는 사례를 확인했다. 기존의 넓은 문자 집합 대신 안전한 한글·숫자·구두점 집합으로 로컬 생성 문법을 좁혔다. 따옴표/역슬래시 회귀는 실패를 먼저 확인하고 수정 후 통과했다. 기존 실패 7건을 **같은 기록·revision·feedback ID**로 재생성해 7/7이 `READY`로 복구됐다. [복구 비교](rag-api-grammar-recovery.json)를 남겼다. 이 7건의 새 답변을 독립적인 문헌 일치 점수로 다시 평가하지 않았다.

최종 생성 문법은 첫 48건 실행 때와 다르다. **최종 설정에 대한 새로운 독립 48건 점수는 없다.** 첫 결과를 소급해서 성공으로 고치거나 재시도 횟수를 독립 표본 수에 더하지 않았다.

## 7. 실제 인증·수정·보존·복구 검증

| 검증 | 실제 결과 |
|---|---|
| 비로그인/잘못된 JWT로 기록 조회 | 각각 401 |
| 다른 회원의 기록 조회/수정 | 각각 403 |
| 다른 회원의 코칭 조회/재생성 | 각각 404 |
| READY 재생성 | 409, 기존 상태 유지 |
| 수정 경합 | revision 1/2는 STALE, 최신 3만 READY |
| 선택 관수 상세 제거 | 조회 null, AI 문맥 미입력, 실제 `watering_record` 잔여 행 0 |
| 수정 중 생성 실패 | HTTP500을 CHAT_UNAVAILABLE로 표시; 기록·문맥 보존 |
| 같은 최신 기록 재개 | 기존 feedback ID/revision으로 재생성 READY |
| 과거 CPU 실패 기록 재생성 | 동일 feedback ID로 READY 복구 |
| 전용 환경 일반 중지·재시작 | 37개 테이블의 행 수/내용 해시, 합성 ID, 모델 식별값 일치 |
| 컨테이너 down 후 재생성 | 동일 37개 테이블/ID/모델 일치, 볼륨 유지 |
| 백업·별도 임시 DB 복구 | 37개 테이블 행 수/내용 해시 일치, 원본 불변, 만든 임시 복구 DB만 제거 |
| 문서 재적재 | 26개 중 추가 0, 전체 DB 내용도 불변 |
| 잘못된 DB 식별값 | 실제 DB를 읽은 뒤 거부, DB 쓰기 없음 |
| 기존 환경 보호 | 전용 프로젝트 외 10개 컨테이너의 ID·생성/시작/종료시각·상태·마운트 불변 |

처음 수정 경합 검사는 모델 서버 오류로 중단됐다. 성공한 것처럼 덮지 않고 실패 응답과 로그를 보존한 뒤 동일 기록부터 복구했다. 첫 실행의 뒤 단계는 실행하지 않았고, 재개 과정에서 접근 차단 검사를 다시 실제 호출해 결과를 남겼다.

최종 DB에는 합성 회원 2명, 농장 1개, 작물 3개, 영농 기록 96개, 코칭 revision 98개, 문단 벡터 26개가 있다. **96개는 여러 개발·실패·회귀 실험을 포함한 누적 저장 수이며 독립 평가 건수가 아니다.** 일부 기존 실패 코칭은 재생성돼 현재 DB 상태가 첫 평가 파일과 다르다. 첫 평가의 원시 파일은 당시 결과를 그대로 보존한다. 최종 확인 시 PENDING은 0이며 최신 수정 기록 revision 3의 READY 응답을 실제 인증 조회했다.

완료된 기록·답변의 보존과 진행 중 요청의 재실행은 다르다. 기존 비동기 큐는 메모리에 있으므로 앱 종료 중 PENDING 요청이 자동 재실행된다고 보장하지 않는다. 이번 보존 비교는 생성이 끝난 상태에서 수행했다.

## 8. 검사 명령과 코드 리뷰

실제 수행한 핵심 명령은 다음과 같다. 원시 실행 로그는 `.local/rag-api/`에 남아 있다.

```bash
python3 scripts/test-rag-api.py
python3 scripts/test-evaluate-rag-api.py
./gradlew :application:test --tests '*RecordFeedbackGenerationServiceTest' --offline --console=plain --no-daemon --max-workers=1
./gradlew :api:test --tests '*RagApiLabSchemaTest' --offline --console=plain --no-daemon --max-workers=1
./gradlew test --offline --console=plain --no-daemon --max-workers=1
python3 scripts/evaluate-rag-api.py --split evaluation --run independent-v1
python3 scripts/analyze-rag-api.py --split evaluation --run independent-v1
python3 scripts/verify-rag-api-lifecycle.py
python3 scripts/rag-api.py verify-restore
python3 scripts/rag-api.py ingest
```

`independent-v1`은 보존된 최초 실행명이다. 최종 설정에서 재실행하면 설정 차이를 감지해 중단한다. 사용자가 새 실험을 할 때는 새 `--run` 이름을 쓴다. 같은 사례를 새 독립 표본으로 부르지 않는다. 라이프사이클 도구는 이미 결과/중단 기록이 있으면 새 기록을 만들지 않고 확인을 요구한다. 현재 결과는 실패 후 `.local/rag-api/lifecycle/recover.py`로 **동일 ID부터** 재개한 것을 함께 포함한다. 일반 실습은 사용 안내의 submit/get/update/regenerate 명령으로 하면 된다.

- Python 보호/관측 회귀: **6+6건 통과**.
- 모델 호출 실패 분류: **20건 통과**. HTTP 제공자 오류 추가 회귀는 20건 중 1건의 실패를 먼저 확인했다.
- 로컬 생성 문법: **1건 실패 재현 → 수정 후 통과**.
- 최종 루트 검사: **총 1,416건, 통과 1,400, 실패/오류 0, 스킵 16**. 최종 명령은 35초에 성공했다. 변경 없는 모듈은 Gradle 캐시를 재사용했다.
- 기본 실행의 스킵 16건: PostgreSQL 기록 검증 13, 기존 실제 검색 1, 보존 검색 실습 1, 벡터 smoke 1. 별도 환경을 명시해야 하는 기존 검사들이다. 이전 단계 결과를 재사용하고 이번 전용 실제 API·DB·모델·재시작 검사는 위의 명시적 도구로 따로 실행했다. 스킵을 통과 건수에 넣지 않았다.
- 실제 날씨·외부 인증·음성·사진·메일·보고서 AI, 전문가 판정, 실제 농장 효과, 대규모 부하, 534작물 전체 품질은 미실행이다. 승인한 로컬 합성 실습 범위 밖이다.

독립 코드 리뷰는 읽기 전용으로 한 번 수행했다. 다음 4건을 수정하고 관련 회귀/실행으로 확인했다. 농업 답변을 전문가가 검증했다는 의미는 아니다.

1. POST 성공 뒤 GET 실패를 생성 거부로 기록하던 평가 집계: 생성 ID와 200을 유지해 조회부터 재개하도록 분리.
2. Spring AI의 제공자 HTTP 예외 누락: 호출 실패 분류 추가.
3. 재개 후 짧은 조회 시간을 전체 지연으로 혼합: 별도 관측 시간으로 기록하고 전체 지연 분모에서 제외.
4. wrapper 종료만 보고 API 종료로 간주: 실제 Java 프로세스와 API 포트 종료까지 확인하고, 남으면 실행 정보를 유지한 채 중단.

| 검증한 DB 백업 | `.local/rag-api/backups/20261115-083031-57b924b6.dump` (600) |

백업 SHA-256은 `94ba9b34a60e0a06a7cf464bdaf8cee0b57995fd9f2057ea7afb319565f71911`이다. DB 백업에는 모델 파일·원문·`.env`가 들어 있지 않는다. 이 폴더들과 볼륨을 함께 보존해야 같은 환경을 다시 사용할 수 있다. 도구는 기존 DB에 백업을 자동으로 덮어쓰지 않고 별도 임시 DB에서 복구를 검증한다.

macOS Ollama는 `.local/rag-api/native-app/Ollama.app`에만 두었다. 공식 ZIP SHA-256 `4715531bc49d21337381b193765041e535a9fb4716f84e5d6eccc3a9af1b5303`, 서명·공증 확인 후 앱 내부 CLI를 실행했다. 별도 CLI 압축본은 실행 심사에서 앱으로 인정되지 않아 사용하지 않았다. `/Applications`, PATH, 로그인 항목, Docker 전역 자원, 보안 설정은 변경하지 않았다.

자원 확보를 위해 Chrome에 정상 종료를 요청해 성공했다. 카카오톡·Notion은 실행 중이 아니었다. 사용자 앱을 강제 종료하지 않았고 Codex·Docker·시스템 프로세스를 정리하지 않았다. 사용량 제한으로 새 명령의 자동 승인이 거절된 구간은 우회하지 않고, 예약된 06:40 재개에서 이어갔다.

다음 큰 작업은 **새 모델이나 문서를 무작정 늘리기 전에 답변 정책과 평가 기준을 정하는 것**을 제안한다. 승인 없이 다음 내용을 제품 코드에 추가하지 않았다.

- 기록이 부적절하거나 근거가 부족해도 반드시 ‘잘한 점’을 내야 하는지, 사실 설명/판단 보류를 어떻게 표현할지.
- 품종·재배 방식·생산 목적·토양·면적·성분이 없을 때 확인 질문, 보류, 일반 안내를 어디까지 허용할지. 새 구조화 필드는 API 계약 변경에 해당한다.
- 작물명 외에 품종·수확 부위·단계 조건을 검색에서 어떻게 적용할지. 근거가 없는 조합을 억지로 성공 사례로 만들지 않는다.
- 사람이 기대 근거와 판정 예시를 검토하고, 조정에 사용하지 않은 새 평가 사례로 최종 설정을 확인할지.

이번에 얻은 것은 **직접 조작 가능한 보존 환경과 실패까지 확인 가능한 검증 자료**다. 검색 성공을 답변 정확도라고 하거나, 이 로컬 실험을 원래 팀원의 실제 서비스 성능이라고 표현하지 않는다.

Git 작업은 `chore/record-feedback-local-api`에서 했다. 기존 검증 커밋을 보존하고 `ff91b87`(전송 오류), `8a89891`(제공자 HTTP 오류), `ac27766`(실습 설정·테스트·도구)을 역할별로 로컬 커밋했다. 이 결과와 출처·실행 문서는 별도 문서 커밋으로 남긴다. **push·PR·병합·배포는 수행하지 않았다.**
