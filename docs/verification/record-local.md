# 영농 기록 로컬 PostgreSQL 검증

## 목적과 범위

작업 8종의 JSON 입력이 API 컨트롤러·검증기·실제 서비스·PostgreSQL을 거쳐 조회 응답과 AI 입력까지 전달될 때 값과 단위를 보존하는지 확인한다. **문서 검색이나 실제 AI 답변 품질을 검증하는 작업은 아니다.**

사용자가 승인한 의미상 `totalSprayAmount`는 농약과 물을 혼합한 최종 살포액 전체량이다. 기존 프롬프트의 “약을 섞은 물의 양” 표현은 요청에 따라 변경하지 않고 관찰 사항으로 남긴다. 가상 농약·병해충·비료·기록은 사용 적합성이나 실제 사용법의 근거가 아니다.

## 실행

필요 조건: Java21, Python3, 실행 중인 Docker, 로컬에 존재하는 `pgvector/pgvector:0.8.5-pg16` 이미지, 프로젝트의 기존 Gradle 의존성 캐시. 새 라이브러리 의존성은 없다.

저장소 루트에서:

```bash
python3 scripts/verify-record-local.py
```

실행기는 매번 임의 이름의 새 컨테이너와 메모리 기반 독립 DB를 만든다. 포트는 `127.0.0.1`의 임의 포트다. 기존 컨테이너나 볼륨을 재사용하지 않는다. DB 사용자·비밀번호는 실행 시 생성/설정하며 비밀번호는 권한0600인 임시 환경 파일로 전달한다. 완료·실패 시 이 실행이 만든 컨테이너만 정리한다.

테스트에서 스키마를 만들기 **전에** loopback 주소·전용 DB명·실행별 소유 확인 토큰을 검사한다. 검증용 `create-drop`을 기존 DB에 수동 적용하지 말고 위 실행기를 사용한다.

테스트 클래스는 `RUN_LOCAL_RECORD_VERIFY=true`가 있을 때만 실행된다. 기본 `./gradlew test`에서는 이 클래스가 건너뛰어진다. 실제 PostgreSQL 검증 성공 여부는 별도 실행 결과로 확인해야 한다.

```bash
./gradlew test --offline --console=plain
```

## 실제로 사용하는 부분과 제외한 부분

- 실제: Spring MVC 요청 역직렬화·Bean Validation·컨트롤러·GlobalExceptionHandler, 기록 서비스/트랜잭션, JPA, PostgreSQL16, 저장 후 별도 요청 조회, `RecordFeedbackContextAssembler`, `RecordFeedbackPromptBuilder`.
- HTTP 처리는 `MockMvc`의 실제 DispatcherServlet로 실행한다. 별도 TCP 포트에 API 서버를 띄우거나 외부 클라이언트로 접속하는 검증은 아니다.
- 인증 필터는 이 테스트에서 비활성화하고 문자열 principal인 테스트 회원을 사용한다. 로그인·JWT·OIDC 보안을 검증했다고 해석하지 않는다. 서비스의 회원 소유권 검사는 실제로 실행한다.
- 보고서 재계산과 비동기 피드백 준비 리스너는 테스트 대역이다. 보고서 정합성·비동기 생성 수명주기는 이번 통합 검증의 대상이 아니다.
- 날씨와 시각은 고정된 합성값이다. 외부 날씨 실호출과 장애 대응을 검증하지 않는다.
- ChatModel·EmbeddingModel·VectorStore는 대역으로 교체하고 생성·임베딩·검색 호출이 발생하지 않는지 확인한다. 메일·미디어·외부 로그인 API를 호출하는 기능도 실행하지 않는다.

## 입력 자료와 검사

`api/src/test/resources/verification/record-cases.json`에는 8개 유형의 대표9사례가 있다. 심기는 씨앗/모종을 나눴다. 여기에 실제 enum의 모든 허용값을 입력하여 DB·응답·AI context의 값과 단위를 대조한다.

`record-rejections.json`에는 누락·상충·최소값·DB 경계의 예상 상태코드와 오류코드를 명시한다. 기대값을 제품 코드에서 계산하지 않는다. 거부된 요청은 공통 기록·모든 상세·피드백 행 수가 변하지 않았는지 확인한다. 수정 실패 시 기존 상세 값이 유지되는지도 별도로 확인한다.

- 관수/제초: 상세 없음, 빈 객체, 일부 필드.
- 심기: 조건부 수량과 반대 그룹 금지, 단위 생략.
- 시비: 자유 자재명·양·단위·방식.
- 병해충: 농약량 G/ML, 총살포량 ML, 병해충 미선택, 없는 ID, 등록관계 없는 가상 조합.
- 수확: 수량 모름/null, 기본 출처, 수확 부위와 작물 기본 부위 불일치, 기간·최종 수확 true/false.
- 수정: 같은 유형 변경, 상세 생략, 작업 유형 변경, 실패한 수정의 이전값 보존.
- 소유권: 다른 회원의 조회·수정 및 타인 농지로 생성 거부.
- 경계: 메모29/30/500/501자, 수량0/0.009/0.01, 긴 자재명, 소수 다섯째 자리, 수량 정밀도 초과.

## 결과 읽기

실행 결과는 Git 추적 대상이 아닌 `api/build/record-local-verification/`에 생성된다.

| 파일 | 내용 |
|---|---|
| `comparisons.json` | 합성 입력, DB 공통/상세 행, 조회 응답, AI context와 프롬프트, 거부·관찰 결과 |
| `infrastructure.json` | 이미지ID/digest, 임시 컨테이너, 로컬 포트, 실행 종료코드, 테스트 집계 |
| `junit.xml` | 이번 PostgreSQL 실행의 JUnit 결과 보관본 |
| `gradle.log` | 실제 Gradle 실행 로그 |

`comparisons.json`의 비교 행 수는 JUnit 테스트 수와 다르다. 하나의 테스트가 여러 누락·수정 사례를 실행할 수 있다. 개별 캡처가 있어도 전체 성공은 실행 종료코드0과 JUnit 실패/오류0을 함께 확인해야 한다. 기본 전체 테스트 실행은 로컬 PostgreSQL 실행 증거를 대체하지 않는다.

## 결과에서 바로 고치지 않는 사항

확인한 제품 동작은 그대로 기록한다. 명칭 수정·수량 정책·입력 상한·등록관계 검증·카탈로그 변경은 이 작업의 승인 범위가 아니다. 변경이 필요하면 재현 결과와 별도 계획을 먼저 제시한다.

## 학습 순서

1. 대표 입력 한 건을 읽고 어떤 작업을 기록했는지 설명한다.
2. DB 공통행과 상세행이 왜 나뉘었는지 확인한다.
3. JSON 누락/null/기본값이 DB와 응답에서 어떻게 나타나는지 비교한다.
4. AI에 전달되는 정보와 빠지는 정보를 확인한다.
5. 실제 관찰 결과만으로 개선 필요성과 한계를 설명한다.

다음 큰 작업은 별도 승인을 거쳐 공식 농업 문서 선정·적재·실제 검색 비교를 수행한다.
