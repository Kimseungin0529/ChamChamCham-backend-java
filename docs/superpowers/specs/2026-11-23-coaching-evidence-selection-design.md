# 기록 코칭의 근거 적합성 개선 설계안

상태: 접근 방향 선택 후 2026-11-23 사용자 ㄱㄱ로 첫 구현 단위 승인. 승인된 첫 단위의 구현·검증·리뷰와 로컬 커밋을 완료했다. 후속 실제 검색/답변/API 개선은 승인 전이다.

## 의도와 선택

사용자는 대화형 챗봇을 만드는 대신, 기존 기록 코칭이 요청 의도를 파악하고 필요한 자료를 조사한 것처럼 근거 있는 유용한 안내를 제공하기를 원한다. 개발 중 자료 조사·대조·보완은 에이전트가 수행한다. 요청마다 서비스가 인터넷을 자동 검색하는 기능은 이번 범위에 포함하지 않는다.

고려한 접근은 모델/프롬프트 우선 교체, 근거 선별부터 개선, 대화 기능 우선 추가였다. 사용자는 근거 선별부터 기존 기록 코칭의 정확성을 높이는 방향을 선택했다. 큰 모델의 효과는 추후 동일 조건으로 비교하며, 지금 새 모델을 내려받거나 학습하지 않는다.

## 현 상태와 첫 단위의 목표

- 제품 검색은 기술문서와 작물명/GENERAL을 필터링하며, 여러 질의의 결과를 문서 ID로 중복 제거한다.
- 작물 문맥에는 품종 필드가 없다. 메모의 추정이나 문서의 품종을 사용자의 품종으로 채우면 안 된다.
- 보존 자료는 원문 9개/문단 26개이며, 최신 실험 후보는 유용성 감소로 미채택됐다.
- 먼저 문단별 적용 조건을 근거 문장과 연결하고, 고정된 검색 후보 안에서 조건 충돌을 구분하는 재현 가능한 실험을 만든다.
- 이 단위는 검색 순위·새 문서의 검색 회수율·답변 정확도·실제 API 성능의 개선 완료를 입증하지 않는다.

## 첫 구현 단위

1. 보존 원문·선택 문단·해시를 읽고 26개 문단을 전부 대조한다. 없거나 해시가 다르면 원본을 덮어쓰지 않고 해당 자료를 제외/보류한다.
2. 작물/종, 품종, 작업, 수확 부위, 생육 단계, 재배 조건, 지역, 발행 시점, 제한 사항을 문단별로 기록한다. 각 제한은 원문 위치·인용을 연결한다. 미표시와 명시적 제한 없음은 구분한다.
3. 부족한 관계는 농촌진흥청·농사로·기술원·농약안전정보시스템 등 공개 공식 자료를 먼저 조사한다. 유료·계정 신청·비공개 접근은 하지 않는다. 필요한 경우 대학·연구기관의 1차 자료로 보완한다. 문서 수를 채우기 위한 수집은 하지 않는다.
4. 추가 원문은 Git 제외된 `.local/rag-api/evidence-selection/sources/`에 새 파일로 보존하고 조회 시각·URL·SHA-256·선택/제외 이유를 남긴다. 기존 corpus와 DB는 덮어쓰거나 재적재하지 않는다. 원문/선택 본문 자체는 이 단위에서 Git에 넣지 않는다.
5. test 소스에만 선택기를 만든다. 입력 사실과 문단 조건을 대조하여 APPLICABLE/CONDITIONAL/EXCLUDED와 사유를 반환한다. 먼저 문단 ID와 선택 본문 SHA-256이 조건 주석 당시와 일치해야 하며 불일치는 평가 오류로 중단한다. 유효한 문단에서 작물·품종·부위 등 알려진 값의 명시적 충돌이 하나라도 있으면 EXCLUDED를 우선한다. 그 외 필수 조건 미확인·규칙 누락·해결되지 않은 문헌 상충은 CONDITIONAL이다. 남은 문단만 APPLICABLE이며 제한이 없는 일반 관찰 안내는 보존한다.
6. 메모에 명시된 사실을 사례에 수동 주석할 수 있으나 원문 위치와 일치해야 한다. 기대 근거·정답·판정 이유는 선택기에 전달하지 않는다. 자연어 전체를 해석하는 추출기나 새 API 필드는 만들지 않는다.
7. 기존 사례를 개발용으로 사용하고, 조건 충돌/누락/일반 안내를 포함한 새로운 평가 상황은 입력과 기준을 먼저 고정한다. 목표 48개이며 불가능하거나 미확보인 조합은 이유를 공개한다. 평가를 보고 수정하면 해당 세트는 개발용으로 전환한다.

선택기는 받은 후보만 분류하며 순위를 바꾸거나 새 근거를 만들어내지 않는다. CONDITIONAL 자료를 모델에 어떻게 전달할지는 다음 답변 개선 단위에서 결정한다. 현재 제품의 빈 근거 차단·프롬프트·응답 스키마는 보존한다.

기존 문단과 새로 검토한 문단은 `.local/rag-api/evidence-selection/corpus.json`에 평가 전용 사본으로 묶는다. 각 문단은 출처 ID·문단 ID·본문 해시·조건 주석을 연결한다. 원문 경로는 기존 corpus와 새 sources 폴더 두 곳으로 제한한다. 통제 후보에 새 문단을 수동 포함한 것은 검색 성공으로 세지 않는다.

## 첫 단위 완료 기준

- 26개 문단의 확인/보류/미확보 상태와 각 사유가 남는다. 새 자료는 기존 자료와 식별해서 센다.
- 명시적 조건 충돌 제외, 미확인 조건 표시, 적용 가능한 일반 안내 보존을 각각 건수/분모로 보고한다.
- 후보에 필요한 문단이 없었던 사례는 선택기 실패와 분리한다. 문서가 없거나 전부 조건부인 경우를 성공 안내로 세지 않는다.
- 실제 자료의 의미 판정은 에이전트 자체 검토이며 전문가 검증이 아님을 명시한다. 사용자가 다시 확인할 대표 사례를 제공한다.
- Python/Java 관련 검사와 최종 `./gradlew test`를 실행한다. Docker가 필요한 검사는 미실행 사유를 표시한다.
- 결과·실행법·변경 근거를 보존하고, 개선 효과가 없으면 미채택으로 보고한다.

## 이어질 큰 작업

1. 실제 검색: 사용자 승인으로 전용 환경만 재개한 뒤 별도 평가 테이블/버전에 후보 수집·조건 선별·순위를 비교한다. 기존 corpus/벡터는 보존한다. 현 Spring AI 1.1.8에서 가능한 기능을 우선 사용한다.
2. 답변 개선: 확실한 일반 안내와 필요한 확인을 함께 제공하도록 같은 모델로 비교한다. 근거 없는 행동/수치 감소와 유용성 유지를 함께 측정한다. 변경된 출력 정책은 실험용으로 먼저 검증한다.
3. 최종 API 평가: 새로 분리한 상황에서 인증→기록→실제 검색→생성→조회와 보존을 다시 확인한다. 첫 단위의 48개 결과를 새 독립 답변 평가로 재사용하지 않는다.

## 변경·자원·Git 경계

- 첫 단위는 test 소스, 합성 사례, 출처/조건 목록, 실행 도구, 문서만 변경한다. 제품 src/main, 공개 계약, DB, 농약 명칭·사용 적합성 정책은 바꾸지 않는다.
- Docker/API와 모델은 첫 단위에서 시작하지 않는다. 현재 데이터·모델·백업을 삭제하지 않는다. 새 설치/다운로드는 하지 않는다.
- 실행 승인 후 로컬 dev와 기존 검증 커밋의 관계를 확인하고 `chore/coaching-evidence-selection` 브랜치를 준비한다. 기록 보존을 위해 기존 커밋을 유지하며, 예상 밖 분기/충돌이 있으면 근거를 보고한다. 네트워크 fetch/원격 쓰기를 자동 수행하지 않는다. 최신 원격 dev 여부를 확인 못 하면 이를 명시한다.
- 승인 후 테스트/도구와 문서를 나눠 로컬 커밋한다. push·PR·병합·배포는 하지 않는다.
- 최초 문서 두 개는 사용자가 요청한 계획 산출물이다. 구현과 Git 변경은 위 범위 승인 후 진행한다.
